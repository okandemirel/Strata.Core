# Reddedilen Bulgular (Refuted)

Doğrulama sırasında çürütülen iddialar. Yeniden açılmamalı.

## `entitydescriptor-virtual-define-in-base-ctor`

**EntityDescriptor calls the abstract Define() from its base constructor, so derived field initializers have not run yet**

The quoted code exists exactly at lines 16-22, but the described failure does not occur. The finding's central premise — stated in its title ('derived field initializers have not run yet') and its whole failure scenario — is wrong about C#. Unlike Java or C++, C# executes a derived class's instance field initializers BEFORE the base constructor is invoked (C# spec: variable initializers 'are executed immediately upon entry to the constructor and before the implicit invocation of the direct base class constructor'). So in the finding's own example, `private readonly Health _hp = new Health { Current = 5000, Max = 5000 };` is fully initialized by the time the EntityDescriptor base ctor calls Define(), and `Add(_hp)` captures {5000,5000}, not default. Every boss spawns with 5000 HP, not 0. The only residual exposure is state assigned in a derived constructor BODY, which the finding never mentions and which is a much narrower and more visible pattern (and is somewhat discouraged already, since ArchetypeManager constructs descriptors via `new T()`). Since the reported defect, its example, and its impact are all incorrect, this is refuted.

## `benchmark-category-mismatch`

**Benchmark category attributes are inconsistent — the documented "run benchmarks only" command misses all 14 Tests/Benchmarks methods while "functional tests only" runs them**

The central mechanism is backwards. Unity.PerformanceTesting's PerformanceAttribute derives from NUnit's CategoryAttribute with base("Performance") — I read the package source directly. Its own doc comment says 'It will add category "Performance" to test properties.' So the seven `[Test, Performance]` methods in Tests/Benchmarks (ContainerBenchmarks 2, ECSBenchmarks 3, EventBusBenchmarks 2) — precisely the three fixtures the finding flags as having 'no [Category] at all' — DO carry the Performance category and therefore DO run under `-testCategory "Performance"` and are EXCLUDED from `-testCategory "!Performance"`. The headline claim 'the documented run-benchmarks-only command misses all 14 Tests/Benchmarks methods' is false (it misses 7), and the named failure example is false: ECSBenchmarks.CreateEntity_Benchmark is `[Test, Performance]` and does not run in the functional pass. The 'quantifiedImpact' of 14 methods / 25% and '18 long/threaded tests in the functional pass' are both wrong. A residual, much smaller issue does exist — the 7 plain `[Test]` methods carrying `[Category("Benchmark")]` (ComputedPropertyBenchmarks 3, ViewPoolBenchmarks 2, EventBusSubscribeBenchmarks 2) plus the 4 uncategorized Tests/Stress tests are misfiltered — but that is not the finding as written.

## `singleton-threadsafety-cannot-detect-double-construction`

**The parallel singleton stress test cannot detect double construction — it only checks reference equality of the returned instances**

The quoted line 28 and the assertions at 45-49 are accurate, and it is true that the test has no factory-invocation counter. But the stated failure does not occur. The finding quotes Container.cs:311 (the CompareExchange) and stops there, omitting the three lines immediately after it: the losing thread's instance IS disposed. Container.cs:312-316 reads `if (prev != null) { if (instance is IDisposable d) d.Dispose(); return prev; }`. So the failureScenario — '100 concurrent resolves construct 100 instances; 99 are dropped on the floor without Dispose() being called, leaking handles/subscriptions' — is factually wrong for exactly the IDisposable case it names, and the quantifiedImpact 'one leaked instance per losing thread ... unbounded for IDisposable/handle-owning services' is wrong for the same reason. Construct-then-CAS with disposal of the loser is a deliberate, implemented design, not an unguarded hole. A residual observation survives (the test cannot detect that the factory ran more than once, which would matter for a non-IDisposable service with constructor side effects), but that is not the finding as written.

## `nested-scope-benchmark-leaks-scopes`

**Benchmark_ContainerScope_NestedScopes disposes only the innermost of ten nested scopes**

The quoted line 167 is exact and it is literally true that only the innermost scope is disposed (at line 183). But the described failure does not occur, on two counts I verified in the runtime. First, the nine intermediate scopes hold nothing: the loop at 165-168 only calls CreateScope; `Resolve<LocalService>()` is invoked solely on the final `current` inside the measured loop, so every intermediate scope's scoped-instance cache is empty. The claim 'each holding its own scoped-instance cache for LocalService' is wrong. Second, scopes are not registered with any parent — Container.CreateScope (Container.cs:148-151) just returns `new ContainerScope(...)` with no tracking, and Container.Dispose (178+) only drains its own _disposalStack. So there is no 'root container's child list' retaining them; the nine objects are unrooted managed garbage, not a leak. (I also found the benchmark is not actually nested at all — ContainerScope.CreateScope at ContainerScope.cs:130 returns `new ContainerScope(_parent, ...)`, a flat sibling off the same root — but that is a different, unclaimed defect.)
